# v1.5.5 — diagnostics at scale and fail-closed EMS execution

This is the first public release after v1.5.3. It consolidates the previously
unpublished v1.5.4 candidate, so both the managed EMS package and ESPHome
firmware must be updated. The project is now published as
**EMS for Hoymiles HIT-(5–20)L-G3** from
`Kaluzaburza/hoymiles-hit-g3-ems`; stable technical identities remain
unchanged.

To pierwsze publiczne wydanie po v1.5.3. Konsoliduje ono wcześniej
nieopublikowanego kandydata v1.5.4, dlatego trzeba zaktualizować zarówno
zarządzany pakiet EMS, jak i firmware ESPHome. Projekt jest teraz publikowany
jako **EMS for Hoymiles HIT-(5–20)L-G3** z repozytorium
`Kaluzaburza/hoymiles-hit-g3-ems`; stabilne identyfikatory techniczne nie
uległy zmianie.

## User update steps / Kroki po aktualizacji

1. **HACS:** before updating, keep RCEm in shadow mode and disable every
   automatic or scheduled EMS writer. Update
   **EMS for Hoymiles HIT-(5–20)L-G3** to **v1.5.5**. The renamed GitHub
   repository retains the previous URL through GitHub's redirect.
   **PL:** przed aktualizacją pozostaw RCEm w trybie shadow i wyłącz wszystkie
   automatyczne oraz harmonogramowe zapisy EMS. Zaktualizuj
   **EMS for Hoymiles HIT-(5–20)L-G3** w HACS do **v1.5.5**. Po zmianie nazwy
   repozytorium GitHub zachowuje poprzedni adres przez przekierowanie.
2. **Home Assistant:** restart after the HACS update. The integration installs
   managed EMS package **1.5.5** during startup; validate the configuration and
   restart once more when the Repair notification requests it. Keep all
   writers disabled throughout both restarts, then hard-refresh every open
   Hoymiles dashboard tab so it loads frontend URL `v=1.5.5.17`.
   **PL:** po aktualizacji HACS uruchom Home Assistant ponownie. Integracja
   instaluje podczas startu zarządzany pakiet EMS **1.5.5**; sprawdź
   konfigurację i wykonaj jeszcze jeden restart, gdy zażąda tego komunikat
   Napraw. Podczas obu restartów pozostaw wszystkie zapisy wyłączone, a
   następnie twardo odśwież każdą otwartą kartę dashboardu Hoymiles, aby
   wczytała URL frontendu `v=1.5.5.17`.
3. **ESP32 / ESPHome:** only after the Home Assistant no-write verification,
   rebuild and upload firmware from the top-level ESPHome file pinned to the
   immutable ref **v1.5.5**. HACS does not flash the ESP32. This step is
   required because v1.5.5 includes the firmware changes from the unpublished
   candidate; it does not replace the separate shared-bus Master/Slave test.
   **PL:** dopiero po odczytowej weryfikacji Home Assistanta skompiluj i wgraj
   firmware z głównego pliku ESPHome przypiętego do niezmiennego ref
   **v1.5.5**. HACS nie wgrywa firmware ESP32. Ten krok jest wymagany, ponieważ
   v1.5.5 zawiera zmiany firmware z nieopublikowanego kandydata; nie zastępuje
   osobnego testu Master/Slave na wspólnej magistrali.
4. **Verification / Weryfikacja:** confirm that the physical EMS mode and the
   complete `4300–4306` block did not change during the update, no execution
   owner became active, and the managed package reports **1.5.5 / Ready**.
   Confirm current RCE, tariff and RCEm results or explicit fail-closed reasons,
   fresh Solcast Day 3 when enabled, all Aurora views, and repeated fresh
   register-4102 reports after the firmware upload. Create two diagnostic ZIPs
   and confirm that they contain the same anonymous installation ID. Do not
   claim per-Slave acknowledgement from Master FC03.
   **PL:** potwierdź, że podczas aktualizacji nie zmieniły się fizyczny tryb
   EMS ani pełny blok `4300–4306`, nie pojawił się aktywny właściciel, a pakiet
   zarządzany pokazuje **1.5.5 / Gotowe**. Sprawdź aktualne wyniki RCE, taryfy i
   RCEm albo jawne bezpieczne powody blokady, świeży Dzień 3 Solcast, jeśli jest
   włączony, wszystkie widoki Aurora oraz powtarzające się świeże raporty
   rejestru 4102 po wgraniu firmware. Utwórz dwie paczki diagnostyczne i
   potwierdź w nich to samo anonimowe ID instalacji. Nie traktuj FC03 Mastera
   jako potwierdzenia każdego Slave'a.

## Diagnostics and longitudinal analysis / Diagnostyka i analiza długookresowa

- At first integration startup, Home Assistant creates one random UUID v4 for
  the entire installation and stores it persistently with
  `installation_id_schema_version: 1`. Every config entry and every later
  diagnostic export use the same ID. It is not exposed as an entity.
- The validated `anonymous_installation_id` is included in native diagnostics,
  `environment.json`, and the main ZIP reports. Redaction deliberately
  preserves this field, while an invalid value is not trusted.
- The ID is not based on a MAC address, serial number, IP address, hostname,
  user ID, config-entry ID, inverter value, or other user configuration. Its
  only purpose is correlating successive packages from the same installation.
- The new bounded, offline analyzer processes up to 100 diagnostic ZIPs in one
  run. It compares RCE, RCEm and tariff-charging decisions, reconstructs
  control runs and coverage windows, clusters relevant log evidence, and
  reports data-quality or safety findings. Archives are not uploaded and
  source paths plus raw identifiers remain hidden by default.
- The dashboard privacy text now explains the ID's limited longitudinal
  purpose and non-identifying origin.

**PL:**

- Przy pierwszym starcie integracji Home Assistant tworzy jeden losowy UUID v4
  dla całej instalacji i trwale zapisuje go z
  `installation_id_schema_version: 1`. Każdy config entry i każdy kolejny
  eksport diagnostyczny korzystają z tego samego ID. Nie jest ono encją.
- Poprawny `anonymous_installation_id` trafia do natywnej diagnostyki,
  `environment.json` i głównych raportów ZIP. Mechanizm redakcji celowo
  zachowuje to pole, ale nie ufa niepoprawnej wartości.
- ID nie jest oparte na adresie MAC, numerze seryjnym, IP, hostname, user ID,
  config-entry ID, wartości z falownika ani innej konfiguracji użytkownika.
  Służy wyłącznie do łączenia kolejnych paczek z tej samej instalacji.
- Nowy ograniczony analizator działa lokalnie i przetwarza jednocześnie do 100
  paczek ZIP. Porównuje decyzje RCE, RCEm i ładowania taryfowego, odtwarza
  przebiegi sterowania oraz okna pokrycia, grupuje istotne informacje z logów i
  raportuje problemy jakości danych lub bezpieczeństwa. Archiwa nie są wysyłane,
  a ścieżki źródłowe i surowe identyfikatory są domyślnie ukryte.
- Tekst prywatności na dashboardzie wyjaśnia ograniczony, długookresowy cel ID
  oraz fakt, że nie pochodzi ono z danych identyfikujących.

## EMS, forecasting and safety changes / Zmiany EMS, prognoz i bezpieczeństwa

- Every delayed RCE, tariff, balancing and RCEm action revalidates policy,
  ownership, conflicts, source freshness, physical mode and its committed plan
  before later writes and after acknowledgements. Off-Grid code `3` has
  priority and is not overwritten by automatic cleanup.
- RCE, tariff and RCEm withdraw `result_current` when a consumed input changes
  during calculation. Configured Solcast entities are tracked dynamically;
  optional Day 3 extends the tariff horizon, while missing or stale Day 3 keeps
  the conservative shorter-horizon fallback.
- Stable physical BMS limits and battery capacity now have explicit provenance.
  Register `4102` uses the 20-second settings controller and reports unchanged
  values; live BMS voltage and current limits remain strictly freshness-gated.
- Battery balancing requires the complete 99.9% hold interval. Execution-owner
  diagnostics describe actual active control, not merely an enabled policy.
- The repository and public title changed, but the Home Assistant domain,
  component directory, entity/service/unique IDs, Store keys, dashboard
  strategy type, ESPHome node names and ESPHome `project.name` remain stable.

**PL:**

- Każdy opóźniony etap RCE, taryfy, balansowania i RCEm ponownie sprawdza
  politykę, właściciela, konflikty, świeżość źródeł, tryb fizyczny i
  zatwierdzony plan przed kolejnymi zapisami oraz po potwierdzeniach. Kod
  Off-Grid `3` ma pierwszeństwo i nie jest nadpisywany przez automatyczne
  sprzątanie.
- RCE, taryfa i RCEm wycofują `result_current`, jeżeli podczas obliczeń zmieni
  się używane wejście. Skonfigurowane encje Solcast są śledzone dynamicznie;
  opcjonalny Dzień 3 wydłuża horyzont taryfy, a jego brak lub nieświeżość
  zachowuje konserwatywny krótszy fallback.
- Stabilne fizyczne limity BMS i pojemność baterii mają jawne pochodzenie.
  Rejestr `4102` korzysta z 20-sekundowego kontrolera ustawień i raportuje
  niezmienione wartości; bieżące napięcie oraz limity prądowe BMS nadal
  wymagają świeżych danych.
- Balansowanie wymaga pełnego okresu utrzymania 99,9% SOC. Diagnostyka
  właściciela wykonania opisuje rzeczywiste aktywne sterowanie, a nie samo
  włączenie polityki.
- Zmieniły się adres repozytorium i publiczna nazwa, lecz domena i katalog
  integracji Home Assistant, identyfikatory encji/usług/unique ID, klucze Store,
  typ strategii dashboardu, nazwy węzłów ESPHome i `project.name` pozostały
  stabilne.

## Parallel acceptance boundary / Granica odbioru równoległego

Parallel EMS requires the ESP32 converter, the Master and **every Slave** on one
physical external Modbus/RS485 bus. The address-`0` FC16 command broadcasts the
complete EMS block `4300–4306` on that wire. A later exact FC03 from the physical
Master is configuration acknowledgement for the Master only; it does not prove
receipt or execution by any Slave.

The shared-bus broadcast path was verified in an earlier two-inverter test
configuration, but this is not a claim of current field acceptance. The full
shared-bus test and aggregate physical-response acknowledgement remain deferred
while field data is collected. After review, that contract will be completed
in a separate hotfix. Registers `258`, `259` and `306` remain fail-closed on a
parallel system until their broadcast semantics are independently proven.

W układzie równoległym konwerter ESP32, Master i **każdy Slave** muszą być
podłączone do jednej fizycznej magistrali zewnętrznego Modbus/RS485. Polecenie
FC16 na adres `0` rozgłasza na tym przewodzie kompletny blok EMS `4300–4306`.
Późniejszy zgodny FC03 z fizycznego Mastera potwierdza konfigurację wyłącznie
Mastera; nie dowodzi odbioru ani wykonania polecenia przez żadnego Slave'a.

Ścieżka broadcastu na wspólnej magistrali została zweryfikowana we
wcześniejszej konfiguracji testowej z dwoma falownikami, ale nie jest to
deklaracja bieżącego odbioru terenowego. Pełny test wspólnej magistrali i
potwierdzenie sumarycznej odpowiedzi fizycznej pozostają odroczone na czas
zbierania danych z instalacji. Po ich przeglądzie kontrakt zostanie uzupełniony
w osobnym hotfiksie. Rejestry `258`, `259` i `306` pozostają fail-closed w
układzie równoległym do niezależnego potwierdzenia ich semantyki broadcastu.
