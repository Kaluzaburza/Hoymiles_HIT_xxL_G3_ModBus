# v1.5.3 — current optimizer results and restored Aurora dashboard

## User update steps / Kroki po aktualizacji

1. **HACS:** update **Hoymiles HIT xxL G3 Modbus** to **v1.5.3**.
   Zaktualizuj integrację **Hoymiles HIT xxL G3 Modbus** do **v1.5.3** w HACS.
2. **Home Assistant:** restart after the HACS update. If Home Assistant still
   reports stale managed assets, run
   `hoymiles_hit_modbus.install_assets` with `overwrite: true`, validate the
   configuration and restart once more. Hard-refresh every open Hoymiles
   dashboard tab so it loads frontend revision 17.
   Po aktualizacji HACS uruchom Home Assistant ponownie. Jeżeli nadal zgłasza
   stare zarządzane zasoby, uruchom akcję
   `hoymiles_hit_modbus.install_assets` z `overwrite: true`, sprawdź
   konfigurację i wykonaj jeszcze jeden restart. Twardo odśwież każdą otwartą
   kartę dashboardu Hoymiles, aby wczytała rewizję frontendu 17.
3. **ESP32 / ESPHome:** v1.5.3 does not change inverter firmware behaviour.
   Systems already running the required v1.5.2 FC03-readback firmware do not
   need another flash solely for this Home Assistant/frontend hotfix. A fresh
   build should use the top-level ESPHome file pinned to **v1.5.3**.
   v1.5.3 nie zmienia działania firmware falownika. Instalacje z wymaganym
   firmware v1.5.2 z odczytami FC03 nie wymagają ponownego wgrywania wyłącznie
   z powodu tej poprawki Home Assistant/frontendu. Nowa kompilacja powinna
   korzystać z głównego pliku ESPHome przypiętego do **v1.5.3**.
4. **Verification / Weryfikacja:** keep RCEm in shadow mode and automatic RCE
   and tariff writes disabled during restart. Verify `result_current`, physical
   freshness/readback diagnostics and the complete Aurora dashboard before
   restoring the previous automation policy.
   Podczas restartu pozostaw RCEm w trybie shadow, a automatyczne zapisy RCE i
   taryfy wyłączone. Przed przywróceniem dotychczasowej polityki sprawdź
   `result_current`, diagnostykę fizycznej świeżości/readback oraz pełny
   dashboard Aurora.

## What changed

- Every executor-backed RCE, tariff and RCEm calculation now carries an input
  revision and a direct before/after fingerprint. A source change immediately
  withdraws permission for new writes; stale output is discarded and only the
  latest snapshot is published with `result_current: true`.
- Cross-optimizer fingerprints contain only the LOAD/price attributes actually
  consumed. Diagnostic state changes therefore cannot create a RCE/tariff
  recalculation loop.
- Frontend revision 17 removes legacy and duplicate strategy resources through
  Home Assistant's live Lovelace collection. If an old bootstrap registered the
  immutable strategy element first, the canonical module upgrades that
  constructor in place and applies the complete Aurora decorator.
- The automation matrix now supplies complete, fresh, non-zero BMS charge and
  discharge contracts for nominal RCE cases. It reports positive power,
  joint-solver calls and controlled export for every representative model.
  Missing, stale, future-dated and exact-zero BMS data remain four explicit
  fail-closed tests outside the nominal scenario count.

## Co się zmieniło

- Każde obliczenie RCE, taryfy i RCEm wykonywane w executorze ma rewizję wejść
  oraz fingerprint przed i po obliczeniu. Zmiana źródła natychmiast blokuje nowe
  zapisy, nieaktualny wynik jest odrzucany, a tylko najnowszy snapshot otrzymuje
  `result_current: true`.
- Fingerprinty między planerami zawierają wyłącznie rzeczywiście używane
  atrybuty LOAD/ceny, więc diagnostyka nie tworzy pętli RCE–taryfa.
- Rewizja frontendu 17 usuwa stare i zdublowane zasoby strategii przez aktywną
  kolekcję Lovelace. Jeżeli stary bootstrap zarejestrował element jako pierwszy,
  pełny moduł aktualizuje go w miejscu i nakłada kompletną dekorację Aurora.
- Macierz automatyki używa pełnego, świeżego i niezerowego kontraktu BMS w
  nominalnych przypadkach RCE oraz raportuje niezerową moc, uruchomienia solvera
  i planowany eksport dla każdego modelu. Cztery przypadki BMS fail-closed są
  testowane osobno.
